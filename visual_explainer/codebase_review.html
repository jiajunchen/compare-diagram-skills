Calls / 02B

Views call coordinators; coordinators own persistence and framework work

This map shows the principal cross-component calls. The full declaration index is linked below the figure.

Who calls whom

  1. The root view starts AppViewModel.load. Tournament and bout screens call save, confirm, import, trim, and playback commands.
  2. ScheduleReviewViewModel.extract calls recognition, parsing, optional on-device model assistance, and proposal validation. It passes only edited drafts to confirmSchedule.
  3. AppViewModel delegates media to BoutImportCoordinator, ClipWorkflow, ClipUploadQueue, and ClipDownloadCoordinator.

The playback branch

BoutPlaybackQueue orders saved clips. AppViewModel.playableURL checks a local export or managed cache and otherwise resolves a private CloudKit download. MediaPlayerModel controls AVPlayer, seek, scrub, and speed; it does not merge clip files.

Pathway / 03A

Launch leads to a confirmed bout list only after review

Manual entry and screenshot recognition both end in editable drafts. The parent decides what becomes a saved bout.

Launch and tournament

  1. AppDependencies.make opens the local model container and wires live services. AppViewModel.load checks the iCloud account and reads local settings and tournaments.
  2. The root view shows setup when local settings are absent. Saving the one fencer name creates or updates AppSettings.
  3. The tournament form calls saveTournament. That method trims and validates the name, inserts or updates the tournament, saves SwiftData, and selects the record.

Schedule and bout creation

  1. Manual entry creates draft opponents and full-order bout numbers. Screenshot entry runs Vision, deterministic parsing, optional Foundation Models assistance, and proposal validation on device.
  2. The parent edits, reorders, removes, or discards drafts. confirmSchedule rejects empty drafts, missing opponents, nonpositive or duplicate order numbers, then inserts new bouts and marks the schedule confirmed.
  3. Confirmed bouts can be edited or deleted in BoutDetailView. There is no separate production “Add Bout” screen; manual creation is inside Import Schedule.

Pathway / 03B

An imported original becomes an independent, replayable clip

Import links to the Photos original. Export makes a new local clip, and private CloudKit stores the edited asset.

Import and create

  1. BoutImportCoordinator.prepareSelections asks PhotoLibraryService for selection metadata and identifiers. Confirmation inserts SourceRecording links; cancellation removes temporary working files.
  2. Opening a source requests a PhotoKit AV asset. ClipWorkflow.createClip validates the trim range and inserts ReviewClip before AVFoundation export.
  3. A successful export sets pendingUpload. ClipUploadQueue synchronizes metadata, saves the CKAsset, and marks the clip available. Temporary cloud errors return to pendingUpload; other failures need attention.

Replay and cleanup

  1. Playback orders independent clips. playableURL uses an existing local export, a managed download, or a new CloudKit download. AVPlayer advances through clips without concatenating files.
  2. Offloading removes only safe local exports and caches after CloudKit confirmation. The record and cloud asset remain, so later playback can download again.
  3. Deleting a clip removes its cloud asset before local record cleanup and queued metadata deletion. Source-record removal is blocked while clips still reference it. Photos originals are not deleted.

Review / 04

Three boundaries deserve a focused test

These are source-based review candidates. They are not device-reproduced failures.

■ Status mismatch

A cloud-only clip can look unedited

BoutImportCoordinator.status returns “Edited” only when some clip has a local export path. A clip reconstructed from CloudKit starts in pendingDownload with no local export path. The bout can therefore show “Ready to Edit” or “Not Imported” while a Play Bout action is still available.

Status logic · Cloud clip mapping

▲ First-load timing

Setup can appear before cloud settings arrive

AppViewModel.load marks local loading complete before it awaits a CloudKit refresh. AppRootView chooses setup when the current local settings are absent. A fresh second device may briefly show setup before the synced fencer name arrives.

Load sequence · Root routing

◆ Scope check

Two modeled paths do not have a production entry point

AppViewModel.addBout is present but production views use Import Schedule and confirmSchedule for manual bout creation. ScheduleExtractionRun is in the schema without a production insertion call. Treat it as a modeled record, not evidence of a persisted extraction history.

What to verify on a device
  1. Sync a saved clip to a second device and compare the bout’s media status with its clip count and Play Bout control.
  2. Delay the first CloudKit settings refresh on a fresh second device and watch for setup appearing or racing with the synced name.
  3. Review whether the schema-only extraction record is planned for a later release or should be removed in a future migration.
